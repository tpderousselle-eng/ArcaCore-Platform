# Deployment health checks

Sprint 24.4 adds health checks to every deployment output generated by Sprint
24. The checks use ArcaCore's existing unauthenticated `/health` endpoint and
do not change backend source.

## Dockerfile

Regenerate the Dockerfile:

```powershell
python -m tools dockerfile
```

The generated image includes a Docker `HEALTHCHECK` that requests
`http://127.0.0.1:<port>/health` with Python's standard library. No `curl`,
`wget`, or additional image package is required. The check includes an initial
start period, timeout, interval, and retry limit.

## Docker Compose

Regenerate the Compose file after regenerating the Dockerfile:

```powershell
python -m tools dockerfile
python -m tools compose
```

The API service checks `/health` on its configured container port. PostgreSQL
uses `pg_isready` with runtime environment values, and the API waits for the
database service to become healthy before it starts. No credential is embedded
in the generated file.

## Kubernetes

Regenerate the Kubernetes manifest:

```powershell
python -m tools kubernetes
```

The API Deployment uses HTTP startup, readiness, and liveness probes against
`/health` through the named `http` container port. The startup probe protects
normal initialization from premature liveness restarts. The PostgreSQL
StatefulSet uses `pg_isready` readiness and liveness probes.

## Scope boundary

Sprint 24.4 does not add or modify application routes, database deep checks,
external dependency checks, metrics, tracing, alerting, ingress, TLS,
autoscaling, managed databases, or CI/CD. The existing `/health` endpoint
remains the application contract for deployment health.

## Local verification

Run the dedicated health-check suite:

```powershell
python -m unittest tools.test_health_checks -v
```

Run every tools test:

```powershell
python -m unittest discover -s tools -p "test_*.py" -v
```
